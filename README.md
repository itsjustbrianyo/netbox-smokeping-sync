# netbox_smokeping_sync

One-way sync of Meraki MX WAN IP addresses from **NetBox** into **SmokePing** targets.

NetBox is the source of truth. 

---

## Prerequisites

- NetBox thats syncing with Meraki, preferably via the [Netbox-Meraki-Sync](https://github.com/itsjustbrianyo/netbox-meraki-sync) script
- Custom URL Field in Netbox named `url_smokeping_meraki` under the **DCIM > Sites** Object Type
- A Read-Only API key from NetBox
- SmokePing Running in Docker

---

## How it works

The script does the following:
1. Reads all NetBox sites and picks out those with `url_smokeping_meraki` set, e.g.
   `https://smokeping.example.com/smokeping/?target=Meraki.Site_Name`
2. Parses the target name from the URL (`Meraki.Site_Name` → section `Meraki`, target `Site_Name`). **The target name always comes from this URL**, never from device names, so SmokePing RRD history is preserved if hardware is swapped.
3. Looks up the site's MX in NetBox:
   - role = `firewall`
   - manufacturer = `cisco-meraki`
   - status = `active`
   - has a primary IPv4
4. Renders the entire Meraki branch into a single include file:

   ```
   + Meraki
   menu = Meraki Sites
   title = Meraki Sites

   ++ Site_Name
   menu = Site_Name
   title = Site_Name
   host = IP.Address.Of.MX
   ```

5. If the output is identical to the current file, it exits. Otherwise it backs up the current file, writes the new one, validates it with `smokeping --check`, and reloads SmokePing. If validation fails, the previous file is restored and SmokePing is not reloaded.

The script runs on the **Docker host**, not inside the SmokePing container. It writes into the bind-mounted SmokePing config directory and uses `docker exec` / `docker restart` for check and reload.

## Directory layout

```
/opt/smokeping/
├── docker-compose.yml
├── config/                         ← mounted into the container
│   ├── Targets                     ← contains the @include line
│   └── Targets.d/
│       ├── meraki.conf             ← generated by this script, do not edit
│       └── meraki.conf.bak         ← previous version (created on each change)
├── data/                           ← RRD files
└── sync/                           ← NOT mounted into the container
    ├── netbox_smokeping_sync.py
    └── netbox_smokeping_sync.env   ← config + NetBox token (chmod 600)
```

`sync/` must not appear in any `volumes:` entry in `docker-compose.yml`; the `.env` file contains the NetBox API token.

## Installation

### 1. Python environment

The script runs with the system Python 3 and needs one library, `pynetbox`.

```bash
sudo apt install python3-pynetbox (or install using a venv and pip)
cd /opt/smokeping/sync
chmod +x netbox_smokeping_sync.py
```

### 2. NetBox API token

Create a **read-only** token in NetBox. The script only reads sites and devices.

### 3. SmokePing include

The Meraki conf lives in its own file, so hand-maintained targets in `Targets` are never touched. In `config/Targets`, the whole `+ Meraki` block is replaced by a single line:

```
@include /config/Targets.d/meraki.conf
```

The `@include` path is the path **inside the container**. `SMOKEPING_INCLUDE_FILE` below is the path of the same file **on the host**.

### 4. Configuration file

Create `netbox_smokeping_sync.env` next to the script:

```ini
NETBOX_URL=https://netbox.example.com
NETBOX_TOKEN=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
SMOKEPING_INCLUDE_FILE=/opt/smokeping/config/Targets.d/meraki.conf
SMOKEPING_CHECK_CMD=docker exec smokeping smokeping --check
SMOKEPING_RELOAD_CMD=docker restart smokeping
```

```bash
chmod 600 netbox_smokeping_sync.env
```

The script loads this file automatically from its own directory. Real environment variables take precedence over values in the file. A different file can be passed with `--env-file`.

## Configuration reference

| Variable | Default | Purpose |
|---|---|---|
| `NETBOX_URL` | *(required)* | NetBox base URL |
| `NETBOX_TOKEN` | *(required)* | NetBox API token (read-only is sufficient) |
| `SMOKEPING_INCLUDE_FILE` | *(required)* | Host path of the generated include file |
| `NETBOX_VERIFY_SSL` | `true` | Set `false` to skip TLS verification |
| `SMOKEPING_URL_FIELD` | `url_smokeping_meraki` | Site custom field holding the SmokePing URL |
| `SMOKEPING_SECTION` | `Meraki` | Top-level SmokePing section; URLs must use `target=<section>.<name>` |
| `SMOKEPING_SECTION_MENU` | `Meraki Sites` | `menu =` for the section |
| `SMOKEPING_SECTION_TITLE` | `Meraki Sites` | `title =` for the section |
| `MX_ROLE_SLUG` | `firewall` | NetBox device role slug for MX appliances |
| `MX_MANUFACTURER_SLUG` | `cisco-meraki` | NetBox manufacturer slug |
| `WARM_SPARE_TAG` | `warm-spare` | Devices with this tag are ignored (see Warm spares) |
| `SMOKEPING_CHECK_CMD` | `docker exec smokeping smokeping --check` | Command that validates the config |
| `SMOKEPING_RELOAD_CMD` | `docker restart smokeping` | Command that applies the config |
| `MAX_CHANGE_PCT` | `25` | Abort if more than this % of targets would be removed or re-IP'd |
| `MIN_TARGETS_FOR_THRESHOLD` | `5` | The change threshold only applies once at least this many targets exist |

If `docker exec smokeping smokeping --reload` works with your image, use it as `SMOKEPING_RELOAD_CMD` to avoid the short gap in graphs that a container restart causes.

## Usage

Run from the `sync` directory with `sudo`, since the script needs to run `docker` and write to the SmokePing config directory:

```bash
cd /opt/smokeping/sync

sudo python3 ./netbox_smokeping_sync.py --dry-run -v  
sudo python3 ./netbox_smokeping_sync.py
sudo python3 ./netbox_smokeping_sync.py --force
```

The script finds `netbox_smokeping_sync.env` next to itself, so it can also be run from any directory using its full path.

| Option | Description |
|---|---|
| `--dry-run` | Log the changes and print a diff; nothing is written or reloaded |
| `--force` | Bypass the `MAX_CHANGE_PCT` safety threshold |
| `--env-file PATH` | Use a different config file |
| `-v`, `--verbose` | Log every site → target → IP mapping and each API call |

### Reading `--dry-run` output

The summary lines come first:

```
INFO ADD     Site_Name_1 = 192.168.1.1
INFO REMOVE  Site_Name_2 (was 192.168.7.1)
INFO CHANGE  Site_Name_3: 192.168.4.1 -> 192.168.4.2
```

Then a unified diff between the current file and the generated one:

- `--- <file>` / `+++ (generated)`: which file is which side
- `@@ -133,18 +136,18 @@`: this chunk starts at line 133 (18 lines) in the current file and line 136 (18 lines) in the generated file
- lines starting with a **space**: unchanged context
- lines starting with **`-`**: will be removed
- lines starting with **`+`**: will be added

SmokePing's own `+` / `++` headers stack on top of the diff markers, so `+++ L4LP-Pontiac` means "add the line `++ L4LP-Pontiac`".

## Scheduling

Add the job to root's crontab (`sudo crontab -e`), since it needs to run `docker` and write to the config directory:

```cron
*/15 * * * * /usr/bin/python3 /opt/smokeping/sync/netbox_smokeping_sync.py >> /var/log/netbox_smokeping_sync.log 2>&1
```

Use full paths in cron, because cron runs with a minimal `PATH` and doesn't start in the script's directory.

Runs with no changes exit immediately and do not reload SmokePing, so a frequent schedule is harmless.

## Safety behaviour

| Situation | What happens |
|---|---|
| Output identical to the current file | Nothing written, no reload |
| Site's MX can't be resolved (missing, no primary IP, ambiguous) | Previous host is **kept** and a warning is logged; the target is never silently dropped |
| Site's MX can't be resolved and there is no previous host | Target is not created; warning logged |
| URL field isn't a valid `Meraki.<name>` target | Site skipped; warning logged |
| Two sites point at the same target name | Second site skipped; error logged |
| Too many targets removed or re-IP'd in one run | Aborts (exit 2) without writing; rerun with `--force` if expected |
| `smokeping --check` fails | Previous file restored from `.bak`, no reload (exit 3) |

A target disappears from SmokePing only when no NetBox site's URL field points at it anymore. Its RRD file stays on disk.

## Warm spares


- Devices tagged `warm-spare` in NetBox are ignored.
- If several MXs remain and they share one primary IP (e.g. a virtual IP), that IP is used.
- If several MXs remain with different IPs, the site is treated as ambiguous: a warning is logged and the previous host is kept. Tag the spare to resolve it.

## Maintaining targets

**Adding a site:** set `url_smokeping_meraki` on the NetBox site to `https://smokeping.example.com/smokeping/?target=Meraki.Site_Name` and make sure the site has an active Meraki MX with role `firewall` and a primary IPv4. The next run adds it. Target names may contain letters, digits, `-` and `_` only.

**Removing a site:** clear the URL field (or delete the site). The next run removes the target.

**Renaming a target:** SmokePing stores history in an RRD named after the target, so a rename starts a new, empty graph. To keep history:

1. Update the URL field in NetBox.
2. Run `--dry-run` to confirm the rename.
3. `docker stop smokeping`
4. Rename the RRD, e.g. `mv data/Meraki/Old-Name.rrd data/Meraki/New-Name.rrd`
5. Run the script, then `docker start smokeping` if the reload command didn't already start it.

**Changing an IP:** don't edit `meraki.conf`; fix it in NetBox (or in Meraki, and let the Meraki → NetBox sync update it). Manual edits to `meraki.conf` are overwritten on the next run.

## Troubleshooting

**`no active MX with a primary IPv4 - keeping previous host`**
The site has no device matching role `firewall` + manufacturer `cisco-meraki` + status `active` with a primary IPv4. Check the MX in NetBox: role, status, manufacturer, and whether a primary IPv4 is set.

**`ambiguous: N MXs with different IPs`**
More than one matching MX at the site. Tag the spare `warm-spare`, or fix the role or status of the extra device.

**`is not a valid 'Meraki.<name>' target URL`**
The URL field doesn't contain `target=Meraki.<name>`, or the name has characters other than letters, digits, `-` and `_`.

**`Aborting: X of Y existing targets would be removed or re-IP'd`**
Usually a NetBox problem (API permissions, a bulk edit, a failed Meraki sync). Review with `--dry-run`, then use `--force` if the changes are real.

**`SmokePing config check failed`**
The error output from `smokeping --check` is logged, and the previous file has already been restored. Common causes: the `@include` path in `Targets` doesn't match where the file is mounted inside the container, or the container name in `SMOKEPING_CHECK_CMD` is wrong.

**`Missing required environment variable`**
The `.env` file wasn't found next to the script, or a required key is missing from it.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success (including no changes and dry runs) |
| `1` | Missing required configuration |
| `2` | Change threshold exceeded; nothing written |
| `3` | `smokeping --check` failed; previous file restored |
| `4` | Reload command failed; new file is in place but may not be active |
